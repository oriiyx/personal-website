modbus + tcp from first principles

how a serial protocol learned to ride a byte stream · port 502 · MBAP framing · the handshake · what TCP gave Modbus for free

Where Modbus came from

Modbus was published by Modicon in 1979, designed for the world it grew up in: programmable logic controllers connected by short runs of twisted-pair copper, mostly RS-485, mostly point-to-point or short multidrop buses. The whole protocol assumes a single shared wire where one master talks and one slave answers, bytes arrive in strict order, and message boundaries are defined by inter-character silence (3.5 character-times of idle time = "frame done").

On serial, the wire format is small and rigid: one address byte, one function code, the payload, then a 16-bit CRC. The CRC is essential — analog wires pick up noise, voltage spikes corrupt bits, and the only way the master knows a frame was valid is to recompute the CRC and compare.

Where Modbus had to go

By the late 1990s, every plant had Ethernet. PLCs needed to talk to SCADA workstations across the building, then across the site, then across the internet. The Modbus Organization had two choices: design a new protocol from scratch, or wrap Modbus in TCP/IP and ride the existing networking stack.

They chose the second. Modbus TCP was published in 1999. The bet was that the protocol's application layer — function codes, register addresses, data model — was the part people knew and built devices around. The transport — the serial wire, the CRC, the silence-based framing — was incidental and could be replaced wholesale.

The result: the inner part of the message (the PDU — function code + data) is byte-for-byte identical between Modbus RTU on RS-485 and Modbus TCP on Ethernet. Only the wrapper around it changes.

The real question of this page

The Modbus side you already know — function codes, register types, the BMS register map. This page is about the other side of the stack: the TCP that carries it. Three questions are worth answering before any of the wire-format details make sense:

  1. What does TCP actually give Modbus? (Reliability, ordering, integrity — and what it pointedly does not give.)
  2. How does TCP get set up and torn down? (The three-way handshake, the connection lifecycle, why the spec recommends keeping it open.)
  3. How does Modbus extract messages from a TCP byte stream? (TCP delivers bytes, not messages — the MBAP Length field is the bridge.)
Modbus RTU and Modbus TCP share the same brain (PDU) but completely different bodies (transport, framing, error checking). When you debug a Modbus TCP problem, you need to be clear about which body you're poking at — TCP problems and Modbus-layer problems look similar but live in different places.

What TCP is, in one sentence

TCP is a protocol that turns the unreliable, packet-switched, possibly-reordering, possibly-dropping IP layer into the illusion of a reliable, ordered, full-duplex stream of bytes between two endpoints.

"Endpoint" means an (IP address, port number) pair. "Stream of bytes" means: you write some bytes in on one end, the same bytes come out the other end, in the same order, eventually, or you get an error.

The three guarantees

what you get for free, once a TCP connection is open
Guarantee Mechanism What Modbus gets to assume
Delivery Every byte is acknowledged (ACK). If an ACK doesn't come back in time, the sender retransmits. "If write() returned success, the bytes will arrive — eventually." No retry loop in the Modbus layer.
Order Every byte has a sequence number. The receiver buffers out-of-order bytes and reassembles in order. "Byte N+1 will arrive after byte N, always." Modbus messages cannot get scrambled within a connection.
Integrity Every TCP segment has a checksum over its payload. Corrupted segments are dropped silently and retransmitted. "The bytes I receive equal the bytes the sender sent." This is exactly why Modbus TCP dropped the CRC.

The one thing TCP does not give you

Message boundaries. This is the single most important property to internalize, and it's the one that catches every developer who builds their first protocol over TCP.

TCP is a byte stream. If the sender writes 12 bytes, the receiver may read them as: one block of 12, or two blocks of 6, or 12 blocks of 1, or one block of 8 and another of 4. If the sender writes two messages back-to-back, the receiver may read both halves in one chunk, or both messages in one chunk, or any combination.

This is not a bug. TCP is allowed to coalesce or split bytes however the network, OS buffers, and congestion control feel like. The application — Modbus, in our case — has to recover message boundaries on its own. That problem is the entire reason the MBAP header has a Length field, and it gets its own tab.

Stream, not datagram. UDP gives you datagrams: write N bytes, read N bytes, end of story. TCP gives you a stream: write N bytes, read 1..N bytes, possibly multiple times. Confusing these two leads to bugs that work in the lab and fail in production.

Connection-oriented vs connectionless

TCP is connection-oriented: before any bytes flow, the two endpoints perform a setup ritual (the three-way handshake) to agree they exist, agree on starting sequence numbers, and reserve buffer state in their respective OS kernels. Bytes only flow once both sides are in the ESTABLISHED state. When you're done, you tear down the connection cleanly (FIN/ACK exchange).

The practical implication for Modbus: opening a TCP connection isn't free. There's at least one full network round-trip before you can send a single Modbus request. Closing and re-opening per request would waste that round-trip every time. This is why the Modbus TCP specification recommends keeping the connection open across many requests — the next tab walks through the lifecycle.

Where TCP sits in the stack

When you send a Modbus TCP request, your bytes are wrapped in headers all the way down the protocol stack, sent on the wire, then unwrapped in reverse on the other side. Each layer adds a fixed envelope and trusts the layer above to know what its own bytes mean:

Application
Modbus PDU — function code + data (1 + N bytes, max 253)
Modbus framing
+ MBAP header — Txn ID, Proto, Length, Unit (7 bytes)
Transport
+ TCP header — src/dst port, seq, ack, flags, window, checksum (20+ bytes)
Network
+ IP header — src/dst IP, TTL, protocol=6 (20 bytes)
Link
+ Ethernet frame — src/dst MAC, type=0x0800 (14 bytes + 4 byte FCS)

The pieces interesting to this page are the top two: Modbus PDU + MBAP. Everything below that is "TCP/IP gives me a reliable pipe" — but it's worth knowing the pipe is built from layers, because tools like Wireshark show you every layer and the failure mode at each is different.

The three-way handshake

Before any Modbus request can travel, the client and server must agree they're talking. TCP's setup is called the three-way handshake because it's exactly three segments: SYN, SYN-ACK, ACK. Its job is to synchronize sequence numbers on both sides and move both endpoints into the ESTABLISHED state.

three-way handshake — opening a Modbus TCP connection
Each side picks a random initial sequence number (1000 and 5000 here for clarity — in reality they're 32-bit random values to prevent injection attacks). The SYN flag means "I'm proposing this initial seq." The ACK flag means "I have received bytes up to ack." After the third segment, both sides know each other's starting seq and the connection is open. The very first Modbus request can ride along immediately after — TCP doesn't impose an idle moment.

Why three segments and not two

Two segments would be enough to tell each side the other's sequence number — but it wouldn't confirm that both sides actually received both numbers. The third ACK is the client confirming "yes, I received your SYN-ACK with your seq=5000." Without it, the server can't be sure the client is alive and ready; it would have to wait for the first data segment to find out, and stale connection state would accumulate from clients that vanished mid-handshake.

Three segments is the minimum number that lets each side both send and confirm receipt of an initial sequence number.

Tearing it down — four segments

Closing is symmetric: each side sends a FIN ("I'm done sending") and receives an ACK. Because TCP is full-duplex — both directions are independent — each direction is closed separately. That's four segments total in the textbook case (though the middle two often piggyback into one).

connection teardown — FIN exchange
Either side can initiate close. After step 1, the closing side enters FIN-WAIT and can still receive data (only its send-direction is closed). The connection isn't fully gone until both directions have FIN'd.

What this costs, in time

The three-way handshake costs one full network round-trip (RTT) before any application data flows. On a local Ethernet that's ≈0.1 ms — negligible. Over a slow industrial cellular link it might be 200 ms — significant if you'd been reconnecting per request.

This is the central reason the Modbus TCP spec recommends keeping the connection open. The handshake is cheap as a one-time setup, expensive as a per-transaction cost. A polling loop that opens, sends, reads, closes, repeat is wasting an RTT every cycle.

Persistent connection, then. Open once at service startup. Send many Modbus requests. Reconnect only on error. Most Go Modbus libraries (goburrow/modbus for example) do this by default — you call client.Connect() once, and the underlying TCP socket stays open across many reads.

The core mismatch

Modbus is fundamentally a message-oriented protocol: a request is a discrete thing, a response is a discrete thing, and the boundary between them matters. TCP is fundamentally a stream-oriented protocol: bytes flow, and no one promises that "what I read in one recv() call is what you wrote in one send() call."

Two things can happen on the receiver side that catch new TCP programmers off guard:

scenario A — message split across two reads
// Sender does ONE write of 12 bytes (one Modbus request) write(sock, [00 01 00 00 00 06 01 04 00 01 00 02], 12) // Receiver does TWO reads: read(sock, buf, 1024) → returns 7 bytes: [00 01 00 00 00 06 01] read(sock, buf, 1024) → returns 5 bytes: [04 00 01 00 02]
The OS chose to split delivery. Maybe a packet was dropped and retransmitted with only part of the data. Maybe the network MTU forced two IP packets. Maybe the receiver's buffer was momentarily small. None of these are bugs; all are normal TCP behavior. The receiver code must concatenate and parse, not assume one read = one message.
scenario B — two messages merged into one read
// Sender does TWO writes back-to-back (two Modbus requests) write(sock, [00 01 00 00 00 06 01 04 00 01 00 02], 12) write(sock, [00 02 00 00 00 06 01 03 00 00 00 04], 12) // Receiver does ONE read: read(sock, buf, 1024) → returns 24 bytes: [00 01 00 00 00 06 01 04 00 01 00 02 00 02 00 00 00 06 01 03 00 00 00 04] └────────── message 1 ──────────┘└────────── message 2 ──────────┘
Nagle's algorithm, OS write-buffer batching, or just a fast sender — any of these can pack two logical messages into one TCP segment and hand them to recv() as one chunk. The receiver code must find the boundaries, not assume one read = one message.

The receiver, in other words, needs a way to look at a buffer of bytes and answer: "is there a complete message here yet, and if so, where does it end?" That's framing, and it's the Modbus layer's job.

How to frame messages in a stream — two strategies

Strategy How Used by Tradeoff
Delimiter Read until you see a special byte (e.g. \n) — that byte ends the message. HTTP/1, IRC, SMTP, line-based protocols Simple, but fragile if message bodies can contain the delimiter — you need escaping.
Length prefix Each message starts with a fixed-size field giving the byte length of the rest. Modbus TCP, gRPC, most binary protocols Robust — body can contain any bytes. Requires reading a small fixed header first to know how much to read next.

Modbus chose length prefix. The MBAP header carries a Length field whose entire job is to tell the receiver: "after this header, there are N more bytes that complete the current message."

The Length field counts every byte that follows it — the Unit byte plus the entire PDU. In this example: Unit (1) + PDU (5) = 6, so Length = 0x0006. Critically, the first 6 bytes of every Modbus TCP message are at fixed offsets: you always know where Length lives. That's what makes the framing algorithm possible.

The receive loop, every Modbus client implements something like this

// Pseudocode — buffer-and-parse loop over a TCP socket buf = [] // growing byte buffer loop { n = read(sock, tmp, 1024) buf.append(tmp[0:n]) loop { // drain as many complete messages as we have if len(buf) < 8 { break } // not enough for MBAP header (7) + 1 FC byte length = read_u16_be(buf[4:6]) // Length field at fixed offset 4..5 total = 6 + length // 6 bytes before Length + Length-counted bytes if len(buf) < total { break } // still waiting for the rest of this message message = buf[0:total] process(message) // hand one complete ADU upward buf = buf[total:] // keep any leftover bytes for next iteration } }

Two ideas worth pulling out:

1. The inner loop runs as many times as there are complete messages in the buffer. If two messages arrived merged (scenario B above), the inner loop runs twice on a single read(). If a message is split across reads (scenario A), the inner loop breaks early and the outer loop reads more bytes before trying again. Either case is handled by the same code.

2. You can read the Length field as soon as you have 6 bytes, but the full message isn't there until you have 6 + length bytes. This is why the header field has to come first and has to be at a fixed offset. If Length were a variable-length field (like in some other protocols), framing would be a chicken-and-egg problem.

Most Go Modbus libraries do this for you. You'll call something like client.ReadInputRegisters(addr, qty) and the library hides the buffer/parse loop. But knowing it's there matters: if you ever debug a hang or a malformed-frame error, the bug is almost always in this loop or in something upstream feeding it bytes incorrectly.

Why this design eliminates serial Modbus's silence-based framing

On RS-485, Modbus RTU has no length field. Frames are bounded by 3.5 character-times of bus silence before and after — if there's idle time, the frame is over. That works on a serial wire where you control the timing precisely.

It doesn't work on TCP at all, because TCP is allowed to introduce arbitrary delays. A 50 ms pause between two halves of a write would falsely terminate a frame under silence-based framing. The Length field is the explicit, timing-independent replacement: the message ends when you've read N bytes, not when the wire goes quiet.

The Modbus request is 12 bytes (MBAP + PDU). To put it on the wire takes 58 bytes of headers/trailers below it — a ~5x overhead for a single short request. (This is why protocols designed for tight industrial loops sometimes batch many register reads per request.)

Why no CRC at the Modbus layer

This is one of the cleanest examples of "trust the layer below." Each layer in the diagram above is already checking integrity:

  • Ethernet appends a 4-byte FCS (Frame Check Sequence — CRC-32) to every frame. Corrupted frames are dropped by the NIC before they reach the kernel.
  • IP has its own header checksum (covers only the IP header, but that's enough to prevent misrouting).
  • TCP has a checksum covering its header and its payload. A corrupted TCP segment fails the checksum, gets silently dropped, isn't ACKed, and the sender retransmits.

By the time bytes reach the Modbus layer, they have already survived three independent integrity checks. Adding a fourth (a Modbus-level CRC) would catch essentially nothing the lower layers missed — it would only protect against bugs inside the OS networking stack or inside the Modbus library itself, which is a far weirder failure mode than wire corruption.

So Modbus TCP dropped the CRC. Modbus RTU keeps it because on a raw RS-485 wire there are no lower layers — the analog wire is naked, and the CRC is your only line of defense.

The principle here is worth keeping. When you design a protocol that runs over TCP, don't redo work TCP already does. No CRCs, no retry logic, no sequence numbers (TCP has them), no keep-alives at the application layer unless you genuinely need to detect "the other side's app crashed but its TCP stack is still alive" (which is sometimes real — see the Notes tab).

Port 502 — and why it's special

Modbus TCP servers listen on TCP port 502, registered with IANA specifically for Modbus. The client side uses an ephemeral port assigned by its OS (typically 32768–60999 on Linux). The server's port is fixed so that clients, firewalls, and management tools can identify Modbus traffic by inspection.

Some devices expose configurable ports (5020, 5021, 8502 are common alternatives, useful when one host serves multiple Modbus endpoints). Changing the port doesn't add security in any real sense — it just makes the service less discoverable to lazy scans. The Modbus Organization's Modbus/TCP Security profile, which adds TLS, uses port 802.

Connection limits on slaves

Modbus servers — especially embedded BMS, PLCs, energy meters — usually have a hard cap on simultaneous TCP connections, often 1, 2, 4, or 8. This is a firmware constraint, not a protocol one. If you try to open a fifth connection to a device with a cap of 4, the device either refuses the connection or (worse) silently drops one of the existing ones.

The symptom is mysterious intermittent failures when multiple polling services touch the same device. The fix: one master per device, fan out internally to consumers. For the BMS in this assignment, that's exactly the architecture — one Go service holds the Modbus connection, HTTP handlers share the in-memory state.

Persistent connection, but be ready to reconnect

The spec recommends keeping the TCP connection open, but networks fail. The connection can die at any moment for any of these reasons:

Cause How the client finds out
Server reboots / restarts service RST segment, or socket read returns 0 bytes (clean FIN)
Network outage / cable unplug Eventually — TCP retransmits silently for ~15 min before giving up
NAT/firewall idle timeout Connection "works" until next write, then RST or silent black hole
Server connection-limit eviction Usually RST

The polling loop has to treat "read failed" as a normal event: close the socket, sleep briefly, reconnect, resume. A Modbus service that hangs for 15 minutes because TCP is still in its retransmit-and-hope phase is a service that's failing in production.

Per-operation read timeouts are the standard mitigation. Set a deadline (1–5 s typically) on every Modbus read; if it expires, treat it as a connection-level failure and reconnect. Most Modbus libraries expose this as a Timeout field on the client.

Transaction ID — what it actually enables

The 2-byte Txn ID at the start of the MBAP header is echoed unchanged from request to response. Its purpose is to match responses to requests when multiple are in flight on the same connection.

On classic serial Modbus this didn't matter — one in-flight request per bus, by physics. On TCP you could pipeline: send request 1, send request 2, then receive response 1, then response 2 — possibly even response 2 before response 1 if the server is parallelized. The Txn ID lets the client demultiplex.

In practice most clients are still strict request/response (send, wait for response, send next). But:

  • Even in strict mode, the Txn ID catches the case where a delayed response from a previous request arrives after a timeout — if the Txn ID doesn't match the expected one, the response is discarded.
  • It's how the client knows a response is for this request and not a stale leftover.

Typical implementation: start a counter at 0 (or random), increment per request, wrap at 65535.

Nagle, delayed-ACK, and polling latency

Two TCP optimizations can hurt low-latency request/response patterns like Modbus polling:

Mechanism What it does Effect on Modbus
Nagle's algorithm Delays small writes briefly, hoping to coalesce with the next write into one segment. Small Modbus request might wait 40 ms before being sent if Nagle thinks more bytes are coming.
Delayed ACK Receiver waits ~40 ms before ACKing, hoping to piggyback the ACK on outgoing data. If both sides have these on, you can get the "Nagle/delayed-ACK interaction" — ~200 ms stalls on short request/response sequences.

For Modbus polling, the standard fix is TCP_NODELAY on the client socket — disables Nagle, sends every write immediately. Most Modbus libraries set this for you. If you're seeing weird ~40 ms or ~200 ms stalls between request and response that go away under load, this is the suspect.

Debugging mental model

When something goes wrong with Modbus TCP, the diagnostic question is which layer. Rough triage:

Symptom Likely layer Tool
Connection refused immediately TCP — server not listening / wrong port / firewall nc -v host 502
Connection accepted, then RST TCP — server's connection limit hit, or wrong protocol on port Wireshark; check server connection count
Connect OK, request sent, no response Modbus — server got bytes but couldn't parse, or device is hung Wireshark (Modbus dissector); check server logs
Exception response (FC | 0x80) Modbus — bad address, illegal function, etc. Read the exception code; it's in the response
Wrong values Modbus — endianness, signed-vs-unsigned, register-map misread Cross-check decode against the device spec sheet
Intermittent timeouts TCP — NAT timeout, flaky link, or device firmware Wireshark + packet capture over time

Wireshark has a built-in Modbus TCP dissector that decodes every field of the MBAP header and PDU. On a debugging-resistant problem, capturing 30 seconds of traffic and reading it in Wireshark tells you more than reading source code does.
