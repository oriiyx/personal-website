modbus + BMS from first principles

a backup battery, a Modbus TCP slave, and a register map — decoded

What the task actually asks

A small physical device — the BMS (Battery Management System) — sits on the same network as your service. It has two lithium cells inside it and some control hardware. Your service needs to watch it (read voltages, current) and steer it (turn the charger on/off, configure balancing) over a protocol called Modbus TCP. Then it needs to surface all of that as a normal HTTP API for whoever consumes it next — a UI, an operator, a monitoring system.

So the service is essentially a translator and a controller:

  • Translator: Modbus on one side, HTTP/JSON on the other.
  • Controller: periodically reads sensors, decides whether to enable the charger and how to balance the cells, writes control values back.
  • Recorder: persists historical readings so the API can serve them.

The unfamiliar pieces are the protocol (Modbus) and the domain (what a BMS actually manages and why). Everything else — periodic loops, HTTP routes, a database — you already know how to do.

Why a serial-era industrial protocol on a modern IoT device?

Modbus was invented in 1979 for industrial controllers talking over RS-485 serial wires. It survives because it's brutally simple: a tiny set of read/write operations against a flat array of numbered 16-bit slots. No schemas, no service discovery, no negotiation. A device firmware author can implement the slave side in a few hundred lines of C; a client can talk to it from any language.

When devices got Ethernet, the protocol got wrapped — same operations, same data model, now carried inside TCP packets on port 502. That wrapper is Modbus TCP. The BMS in this task uses it because the firmware on the device probably already spoke Modbus to its internal hardware, and exposing the same map over TCP costs almost nothing.

Mental model: Modbus TCP is "remote memory access for embedded devices." You connect to the device and read or write its registers — a flat array of 16-bit cells — by number. There's no JSON, no objects, no method calls. Just addresses and values.

The shape of the work

end-to-end picture

Your service is the middle box. It speaks a structured, friendly protocol upward (HTTP/JSON) and a register-level wire protocol downward (Modbus TCP). The rest of the page builds up everything you need to understand the right side.

One master, many slaves

Modbus is a request/response protocol with a strict role split. One side initiates (historically called the "master", now usually "client") and the other side only responds when asked (the "slave" or "server"). The device in your task is the slave. Your service is the master.

This has a concrete consequence: the BMS cannot push data to you. It will not notify you when a voltage changes or a fault occurs. If you want to know the cell voltage, you ask. If you want to know it again, you ask again. This is why the task says "periodically poll" — there is no other option.

The four operations you'll actually use

Modbus defines a small set of function codes — one-byte opcodes that name an operation. There are around two dozen total but most devices only implement a handful. For this task you'll use four:

FC Name What it does You use it for
0x04 Read Input Registers Read N read-only 16-bit registers starting at an address Cell voltages, pack current
0x03 Read Holding Registers Read N read-write 16-bit registers starting at an address Read back current charger state or bypass settings
0x06 Write Single Register Write one 16-bit value to one holding register Toggle the charger, set one bypass resistor
0x10 Write Multiple Registers Write N consecutive 16-bit values Set both bypass resistors in one round-trip

You won't construct these bytes by hand — a Go Modbus library will do it. But knowing which function code maps to which operation makes library docs read clearly, and it explains why the register types matter (next tab).

What this gives you

You now know enough to read library documentation. A Go Modbus client API looks roughly like client.ReadInputRegisters(addr, qty) returning a byte slice (two bytes per register, big-endian), and client.WriteSingleRegister(addr, value) for control. The function codes are usually hidden behind named methods; the addresses and quantities map directly onto the table in your task.

Why the read-only / read-write split matters

If a register is an input register, the device is saying "this is a measurement — only I should write it." Your job is to sample it. Writing makes no sense and isn't even an available operation.

If a register is a holding register, the device is saying "this is a setting — you can change it, and the value sticks until you change it again." The device may use the value internally to alter behavior (e.g. when 0x0010 goes from 0 to non-zero, the charger turns on).

This split also implies two different control loops in your service:

  • A read loop against input registers, on a fixed interval — pure measurement.
  • A write path against holding registers, triggered by either (a) the controller deciding to change something, or (b) a manual override coming in via the HTTP API.

You'll also occasionally read holding registers — to know what you previously wrote (after a restart, for instance, or to surface "current settings" in the API).

The address space

Each register type has its own address space numbered from 0 to 65535. So address 0x0001 in input registers is a different register than 0x0001 in holding registers — they don't overlap. The function code disambiguates them: FC 0x04 reads from the input-register space, FC 0x03 reads from the holding-register space.

This is why your task's map is unambiguous even though 0x0001 and 0x0011 are in the same numeric range — the "Type" column tells you which space each address lives in.

Historical wart: older Modbus literature uses 5-digit "logical" addresses where the first digit encodes the type (1xxxx = discrete inputs, 3xxxx = input registers, 4xxxx = holding registers) and the rest is the 1-based address. Modern libraries use the raw 0-based address plus an explicit function code, which is what your task's map shows. If you see 30001 in some doc, it means input register at raw address 0.

Values are uninterpreted 16-bit words

A register is just two bytes. The protocol has no concept of "this register holds millivolts" or "this one is signed." That interpretation is entirely defined by the device's register map document — exactly what the table in your assignment is. Specifically:

  • 0x0001 and 0x0002 hold cell voltages in mV as unsigned 16-bit. Range 0–65535 mV.
  • 0x0003 holds pack current in mA as signed int16. The same bytes that would read as 65000 unsigned read as −536 signed — your code must apply the right interpretation.
  • 0x0010, 0x0011, 0x0012 are RW with unit "—". The map gives no semantics for the value; you'll need to decide on a convention (or ask) — likely 0/non-zero for the charger enable, and either a binary on/off or a level/duty-cycle for the bypass resistors.

What a BMS is for

A lithium-ion cell is a chemistry that delivers a lot of energy per gram, but with narrow safety margins. Charge it above ~4.2 V and it can damage itself or catch fire. Discharge it below ~2.5 V and it permanently loses capacity. Run too much current through it and it overheats. A Battery Management System is the dedicated electronics that keep a battery inside its safe operating envelope — monitoring voltages, currents, temperatures, and gating the charger and load.

In your task, the BMS is already doing the hard low-level work (the safety cutoffs and sensor reads). Your service is the higher-level policy layer: deciding when to charge, and how to keep the two cells matched. The BMS exposes its measurements as input registers and its knobs as holding registers; you read, decide, write.

Two cells in series

The device has two lithium cells wired in series. "In series" means the negative terminal of cell 1 connects to the positive terminal of cell 2, so their voltages add up at the pack terminals.

Two Li-ion cells stacked. The BMS measures each cell individually (because you must monitor each to keep it in safe range), but they share the same current — whatever current flows through cell 1 also flows through cell 2. That shared-current fact is the source of the balancing problem.

Why series? To get usable voltage. One Li-ion cell sits around 3.0–4.2 V depending on state of charge. Two in series gives you a 6.0–8.4 V pack. Devices that need more voltage stack more cells.

Signed pack current

The pack-current register (0x0003) is signed for one reason: current flows in both directions. When the charger pushes energy in, current flows one way; when something draws from the battery, it flows the other way. The sign tells you which.

Sign convention (commonly) Meaning What it tells your controller
Positive current Charging (energy in) Charger is doing work, cells filling
Negative current Discharging (energy out) Load is drawing from battery
Zero / near zero Idle Charger off and no load

The convention can vary by device — some flip the sign. Verify against actual behavior (enable the charger, see whether the value goes positive or negative). For your code, the practical step is to convert the raw uint16 to int16 when decoding:

// raw is the 16-bit register value (uint16) returned by the Modbus library. // In Go, an explicit conversion through int16 gives you the signed interpretation: current_mA := int16(raw)

"Mostly full" — what that constraint means

The task says "keep the backup battery mostly full." This is a deliberate phrasing, not "always full," and the distinction matters:

  • A backup battery needs to be ready. If grid power dies, you want enough charge to be useful. Empty backups are useless.
  • But holding a Li-ion cell at 100% indefinitely accelerates aging — the chemistry is happiest sitting somewhere in the upper-middle of its range.
  • So the right policy is a band, not a setpoint. Charge until cells reach an upper threshold (say ~4.1 V), then disable the charger. Let the pack drift down via self-discharge to a lower threshold (say ~3.95 V), then enable again.

This hysteresis pattern — two thresholds with a gap between them — prevents the charger from rapidly toggling on and off around a single setpoint, which would happen if the cell voltage hovered near the boundary. You'll write to 0x0010 (charger enable) when the upper or lower threshold is crossed, not every poll cycle.

What "full" actually looks like in voltage: a single Li-ion cell is roughly 3.0 V (empty), 3.7 V (nominal/mid), 4.2 V (full). The relationship is non-linear — voltage stays near 3.7 V for most of the discharge then drops fast at the ends — but for your task, voltage thresholds are a fine proxy for state of charge. Pick a "stop charging" threshold below 4.2 V to leave margin.

Why two "identical" cells drift apart

No two cells are truly identical. They come off the production line with slightly different internal resistance, capacity, and self-discharge rate. Over many charge/discharge cycles those small differences compound. After enough cycles, with the same current flowing through both, one cell ends up consistently fuller than the other.

This matters because of a hard constraint: the charger has to stop when the fullest cell reaches its limit, not when the average is at its limit. If cell 1 hits 4.2 V while cell 2 is still at 4.0 V, charging must stop — even though cell 2 isn't full yet. The imbalance directly costs usable capacity.

The bypass resistor — physics-light

A bypass resistor is a resistor wired in parallel with one cell, with a switch the BMS can close. When the switch is closed, the resistor offers an alternate path for current around that cell.

The effect: the fuller cell can be made to discharge slightly through its resistor while charging continues. Some of the charge current "bypasses" the full cell (flowing through the resistor instead) while the lower cell keeps receiving full current. Over many cycles, this nudges the two cells back toward matching voltages.

The whole mental model: the bypass resistor is a controlled bleed valve for one specific cell. Turning it on means "make this cell drop relative to its sibling." Your service decides when each cell's bleed should be on or off based on the voltage difference between them.

This is called passive balancing — passive because the bled energy turns into heat in the resistor (it's not recycled). The balancing currents are small (tens of mA, much less than charge current), so the heat is manageable and the balancing is slow. That slowness is fine: you have hours of charge time to even out cells that differ by tens of millivolts.

The control rule, in words

Translating that into what your service does each cycle:

read cell1_mV, cell2_mV diff = cell1_mV - cell2_mV if diff > THRESHOLD: // cell 1 is fuller bypass cell 1 ON bypass cell 2 OFF else if diff < -THRESHOLD: // cell 2 is fuller bypass cell 1 OFF bypass cell 2 ON else: // close enough bypass cell 1 OFF bypass cell 2 OFF

The threshold prevents constant toggling around tiny differences. Picking a reasonable value (e.g. 20–50 mV) is part of the policy you design.

What value to write for "ON" depends on what 0x0011 / 0x0012 actually accept. The map labels them as RW holding registers with no unit. The two plausible options:

  • Binary: 0 = off, 1 (or any non-zero) = on. Simplest case.
  • Level / duty cycle: 0 = off, larger values = more bleed (e.g. PWM duty cycle 0–100, or 0–65535). Lets you balance more aggressively when cells are far apart.

If the task spec doesn't specify, this is a question worth asking the assignment author — but in absence of clarification, treating it as binary (write 0 or 1) is the safer default since it works in either interpretation.

Balancing only matters when current is flowing

One subtlety: balancing via bleed is most effective during charging, when charge current is replenishing the cells. If both cells are idle (no charge, no load), enabling a bypass just wastes energy from the bled cell — you're discharging it into the resistor while nothing is filling it back up.

So a more careful control rule gates the bleeds on whether the charger is on, or on the sign of pack current. The simple rule above will work and won't damage anything; this is just an optimization opportunity worth mentioning in the design.

The map, row by row

Now that the vocabulary is in place, the task's register table reads as a list of concrete operations.

0x0001 Input register · mV READ Cell 1 voltage

Unsigned 16-bit, millivolts. Range 0–65535 mV (a healthy Li-ion cell sits in 3000–4200 mV). Read with FC 0x04 alongside 0x0002 in a single 2-register read.

0x0002 Input register · mV READ Cell 2 voltage

Same encoding as cell 1. The two cell-voltage registers are consecutive — efficient to read together.

0x0003 Input register · mA · signed READ Pack current

Signed 16-bit, milliamps. Range −32768 to +32767 mA. The sign tells you whether the pack is charging or discharging. Decode with an explicit int16 conversion. Since this lives right after 0x0002, you can read all three input registers in one 3-register call to FC 0x04.

0x0010 Holding register READ / WRITE Charger enable

Write 0 to disable the charger, non-zero to enable it. Toggled by your policy: enable when pack voltage falls below the lower threshold, disable when it crosses the upper threshold (or earlier if any cell hits its individual limit). Write with FC 0x06.

0x0011 Holding register READ / WRITE Cell 1 bypass resistor

Drives the bleed across cell 1. Treat as 0 = off, non-zero = on unless the device spec says otherwise. Set by your balancing logic: enable when cell 1 is meaningfully fuller than cell 2.

0x0012 Holding register READ / WRITE Cell 2 bypass resistor

Same as 0x0011 but for cell 2. The two are consecutive — you can update both in one FC 0x10 write if you want atomic balancing changes, or write each individually with FC 0x06.

Periodic polling — the shape

Because Modbus is request/response with no server-side push, the only way to track the device's state over time is to ask repeatedly on a timer. "Periodic polling" is the loop that does this.

poll cycle
tick
timer fires every N seconds
↓
read
FC 0x04 — read input registers 0x0001..0x0003
↓
decode
cell1_mV, cell2_mV (uint16) · current_mA (int16)
↓

append reading (with timestamp) to storage
↓
decide
run charger policy + balancing policy
↓
write (if needed)
FC 0x06 / 0x10 — only when a setting needs to change
The interval is a tradeoff: too fast wastes CPU and floods storage; too slow misses fast events (a sudden discharge). Cell voltages change on the order of minutes during charging — a poll every 1–5 seconds is typically plenty for a backup system. The interval is a config value, not a constant.

A few practical notes about the loop:

  • Read in batches. A single ReadInputRegisters(0x0001, 3) fetches all three sensor values in one round-trip. Don't issue three separate reads — each costs a TCP round-trip and is a chance for inconsistency between readings taken milliseconds apart.
  • Only write when something changes. Don't blindly write the charger-enable register every cycle; that's network chatter and unnecessary wear. Track the last-written value and write only on transition. (Reading back the holding register after a restart is how you recover state.)
  • Handle errors as transient. Modbus TCP runs over a long-lived connection that can drop. Failed reads should retry; persistent failures should be surfaced as state in your HTTP API ("device unreachable") rather than crashing the loop.
  • Manual overrides need to be honored. If the HTTP API exposes "force charger off," your control loop must respect that flag and not immediately re-enable on the next tick. A simple pattern: the override is itself a piece of state the policy reads.

The service, in one picture

overall architecture
downward — to the device
poll loop (goroutine) → Modbus client → BMS
poll loop → readings store (DB / in-memory ring)
poll loop → policy → Modbus client (writes)
upward — to clients
HTTP handler → readings store (GET state / history)
HTTP handler → override flags → policy (POST manual command)
The poll loop and the HTTP handlers are independent goroutines sharing two pieces of state: the readings store (handlers read it, the loop writes it) and the override flags (handlers write them, the policy reads them). Both directions are concurrency-safe primitives — channels, a mutex-wrapped struct, or an in-memory store with its own locking.
